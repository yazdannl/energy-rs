1. **High — INTENDED mode handling contradicts the owner rule.** Advisory is permitted temporarily and expires into `dry_run`; CURRENT also defaults unknown/missing modes to `dry_run`. Both disable the required protection and balancing charge. **Required change:** define an operational mode policy that never parks the engine in either mode, including startup, invalid configuration, persisted state, API requests, and diagnostic-session expiry. State explicitly how protection remains active during diagnostics.

2. **High — Replan cadence and refusal recovery are unspecified.** CURRENT lists change triggers and a staleness threshold, but INTENDED defines neither a maximum solve interval nor retry scheduling after refusal or unavailable inputs. The release backoff is described without adopting or bounding it. The engine could remain holding without a timely recovery attempt. **Required change:** specify normal cadence, bounded retry/backoff, recovery/reset conditions, and acceptance tests proving replanning continues without another input change.

3. **High — Plan-source selection has no intended contract.** The document addresses mutex failures but never defines which source supplies the executable plan or whether a stored/previous plan can become eligible again after refusal. “Never a silent fallback” also leaves explicit fallback ambiguous. **Required change:** define source precedence, plan eligibility/freshness checks, and invalidation on failed replans; prohibit dispatch of the rejected previous plan until a successful replacement is available.

4. **High — Manual-command failures remain outside the intended failure policy.** CURRENT explicitly discards failed manual replans with `let _ = …`, while INTENDED only says a refused solve holds. It does not specify whether command-triggered failures invalidate execution, schedule retries, or report failure. This leaves a documented silent-no-op path unresolved. **Required change:** apply the same failure and recovery policy to tick- and command-triggered replans, with visible outcomes distinguishing requested, attempted, refused/failed, and successfully installed plans.

5. **Medium — Lock-failure handling does not cover recovery or preserve change detection.** `InputsUnavailable` plus hold is an improvement, but the contract does not say whether failed reads consume change markers or how poisoned versus transiently contended locks recover. A subsequent read could miss the pending change, or poisoning could produce an indefinite hold. **Required change:** preserve unacknowledged input changes, define bounded contention handling and poison recovery/escalation, and test that successful recovery forces a fresh solve before dispatch.

**Verdict: approve with required changes — items 1–5.**
