1. **High — INTENDED feasibility and dispatch contract:** Structured feasibility is specified, but no dispatch rule consumes it, and “operator explicitly accepts” clipping has no defined state or scope. An infeasible or accepted-but-degraded plan could still be dispatched as healthy. **Required change:** Define healthy, degraded/accepted, and infeasible states; specify dispatch eligibility and safe fallback for each. Keep delivery failures separate from planning feasibility, but expose both to dispatch and reporting.

2. **High — Maintenance application and unassigned reasons:** CURRENT adds maintenance after economic planning and recomputes the SoC path and summary, but the INTENDED contract does not require final feasibility validation or classify unassigned maintenance. Reasons such as `no_headroom`, `horizon_too_short`, and `soc_ceiling_below_target` could therefore coexist with an apparently healthy plan. **Required change:** Validate the final assembled timeline after all modifications. Define which unmet maintenance obligations make the plan infeasible versus degraded, and preserve each pack’s reason, deadline, required energy, available energy, and shortfall.

3. **Medium — `terminal_target_unreachable` and clamp semantics:** “A clipped charge is an infeasibility” conflates a modified candidate with an unsatisfied requirement; binding a limit can still yield a valid final plan. Conversely, the existing terminal-error-only check misses other unmet obligations. **Required change:** Evaluate feasibility against hard constraints and required outcomes on the final timeline. Report clipping and binding bounds separately; reserve infeasibility for violated constraints or unmet required outcomes. Specify whether the terminal target is a minimum or an equality and apply the tolerance accordingly.

4. **Medium — Effective terminal target and bound validation:** `max(soft guideline, hard floor).min(ceiling)` correctly prevents a below-floor guideline from becoming an unreachable target **provided floor ≤ ceiling**. If the bounds conflict, it instead returns a target below the hard floor. The supplied plan also lacks explicit regression acceptance cases protecting the distinction between effective terminal target and raw peak guideline. **Required change:** Reject conflicting bounds before solving, use the same effective target in solving and terminal validation, and retain the raw guideline only as separately labelled metadata. Test below-floor, above-ceiling, conflicting-bound, and post-clamp terminal-shortfall cases.

**Verdict: approve with required changes.** These changes are required before implementation. The supplied plan does not establish why the observed all-day zero dispatch occurred; feasibility metadata alone should not be presented as that diagnosis.
