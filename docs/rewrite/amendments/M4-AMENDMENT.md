## Interpretations that need reviewer attention

* S224's 40 % SoC ceiling for `capability_shortfall` is derived from one live observation (31-34 %), not from a calibrated curve. Higher-SoC charge taper (96-98 %) is not classified as a shortfall by M4 and needs its own evidence row before implementation.
* S91 names both "new ramp starts at 12:00:30Z" and `pause_until=12:02:30Z`; those cannot both hold. S234 implements the executable intent (cancel the old pause, ramp the new target immediately) and records the conflict.
* S132 pins reversed status on a nonzero command to `wrong_direction`; the M4 prose rule 1 would call it `status_inconsistent`. The scenario is implemented. A genuine measured-sign/status contradiction with matching command direction remains `status_inconsistent`.
* Echo mismatch (device echoes a different limit) is `Rejected`; echo absence is `Uncertain` and echo plus no flow is `ConfirmationPending` with null applied power. The frozen rows do not name echo mismatch explicitly.
* Invalid status codes are negative `(ac, dc)` pairs; every other unrecognised non-negative pair is `unknown`. The frozen spec names `invalid` but does not define its numeric range.
* M4 implements no target selection, safety decision or write authority. S81-S89's rule precedence and M5/M6 state decisions stay in those modules; the provisional `SafetyGate`/`WriteAuthority` ports only record their answers.
* The SPEC M5 acceptance paragraph names S132/S133/S134/S135 for dry-run, physical limits, neutral evidence and timeouts, but SCENARIOS assigns those ids to M4 flow predicates. M4 follows the scenario table; M5 must renumber its citation when that module lands.

* A read miss builds its row from the tracked `last_command` and pack state: an uncertain pack stays `Uncertain` with the outstanding command identity, a pack with a pending command stays `ConfirmationPending` without claiming a new write, and a pack with neither is `Deferred{reason:no_pending_command}`. A missing observation never manufactures an accepted command.
* Capability shortfall is discharge-only (`command_w < 0`) and is classified only after ramp provisionality: an in-ramp low reading is `Pending{provisional:true}`; a post-deadline low-SoC, `faultLevel=0` reading is `CapabilityShortfall`. Charge derating remains a flow anomaly/shortfall question for a future evidence row.
* Cleanup is a single-claim race between collector and deadline watchdog: exactly one cancels the transport, bumps the generation and releases the transaction. `PackIo::cancel` is mandatory on the provisional port so an in-flight write can be stopped; `Behavior::Late` in tests deliberately ignores cancellation to prove the generation fence works.
